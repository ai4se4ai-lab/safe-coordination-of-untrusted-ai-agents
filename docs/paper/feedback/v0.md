# HIGH LEVEL SUMMARY
---
## Summary
This paper addresses coordination failures in Large Language Model (LLM)-based multi-agent software engineering workflows, such as accepting stale asynchronous replies, merging locally valid but globally conflicting interfaces, and performing redundant workspace regenerations. The author proposes a formal coordination semantics in which agents act solely as untrusted proposers of primitive slot values, while a deterministic controller manages artifact structure via model-transformation rules, tracks exact dependency signatures (encompassing source footprints, selected shared context, and generation contracts), enforces atomic commit guards via optimistic concurrency control (OCC), and gates release through a global publication barrier. The framework is instantiated in a TLA+ specification (checked on bounded instances with TLC and supported by scoped TLAPS lemmas) and a 450-line Python reference controller evaluated using scripted adversarial stubs across a synthetic 4-view document-service case study.

## Strengths
* The manuscript tackles a timely and practically relevant problem in agentic software engineering, recognizing that inter-agent misalignment, asynchronous race conditions, and unverified task completion cannot be solved solely by better prompting or isolated per-output guardrails.
* The synthesis of content-addressed incremental build systems (including early cutoff and exact dependency signatures) with optimistic concurrency control provides a clean conceptual model for distinguishing historical acceptance, current usability, and global publishability in non-deterministic workflows.
* The author exhibits commendable transparency in documenting the exact boundaries of the formal claims and empirical evaluation, explicitly detailing in Table V and Table X which lemmas are mechanized in TLAPS versus proved on paper, and candidly reporting an implementation defect uncovered during randomized testing.

## Weaknesses
* The manuscript constructs its coordination architecture from scratch using dense, bespoke terminology (`source footprint`, `effective observation`, `stamp`, `episode`, `intake`, `contract identity`, `shape of the system`) while overlooking over three decades of foundational Multi-Agent Systems (MAS) literature that already formalizes environment-mediated coordination, passive workspace artifacts, programmable tuple centres, social commitment lifecycles, and electronic institutions; the authors might consider grounding their vocabulary and related work in these established paradigms (Reference Paper: Coordination of Internet Agents: Models, Technologies, and Applications, Andrea Omicini, Franco Zambonelli, Matthias Klusch, and Robert Tolksdorf, 2001; Reference Paper: Artifacts in the A&A Meta-Model for Multi-Agent Systems, Andrea Omicini, Alessandro Ricci, and Mirko Viroli, 2008; Reference Paper: From Tuple Spaces to Tuple Centres, Andrea Omicini and Enrico Denti, 2001; Reference Paper: Agent Communication Languages: Rethinking the Principles, Munindar P. Singh, 1998; Reference Paper: Clouseau: Generating Communication Protocols from Commitments, Munindar P. Singh and Amit K. Chopra, 2020; Reference Paper: Engineering Open Environments with Electronic Institutions, Josep Lluís Arcos et al., 2005).
* Please consider discussing and justifying the use of general-purpose TLA+/TLC verification relative to dedicated multi-agent verification frameworks, automated TLA+ protocol repair pipelines, and modern stateful graph orchestrators (such as LangGraph), while clarifying who is expected to author and maintain the TLA+ specifications, metamodels, transformation rules, and footprint functions in practice (Reference Paper: MCMAS: An Open-Source Model Checker for the Verification of Multi-Agent Systems, Alessio Lomuscio, Hongyang Qu, and Franco Raimondi, 2017; Reference Paper: Model Checking Multi-Agent Systems with MABLE, Michael Wooldridge, Michael Fisher, Marc-Philippe Huget, and Simon Parsons, 2002; Reference Paper: Specification and Verification of Multi-Agent Systems, Mehdi Dastani, Koen V. Hindriks, and John-Jules Meyer, 2010; Reference Paper: TraceFix: Repairing Agent Coordination Protocols with TLA+ Counterexamples, Shuren Xia et al., 2026).
* The formal assurance claims are substantially constrained by the gap between the paper's theoretical ambitions and its mechanized evidence: the central parameterized inductive invariant (Theorem 2), the forward-simulation refinement mapping (Theorem 4), and the cross-episode history-counting bound (Theorem 7) are proved only on paper, while the TLA+ model decouples the typed structural kernel from the protocol transitions, reduces validation to trivial equality ($v = o$), and checks TLC instances of at most $J \le 4$ jobs ($m = 0$ environmental changes for $J \ge 3$).
* The custom semantics introduces a "deferred structural checks" liveness hazard and potential deadlock—which also creates a logical gap in Theorem 8 and Algorithm 1—because candidate normalization checks only currently enabled downstream stages at commit time, allowing an upstream stage to commit a locally valid value while a downstream consumer is suspended that permanently blocks subsequent context reactivation edits.
* The practical applicability and external validity of the domain-correctness and cost-reduction guarantees for real-world software engineering are limited: Assumption A7 ("footprint adequacy" and "validator soundness") is only discharged on a trivial 6-row boolean lookup table where the exact solution is hardcoded into the validator, the strict acyclic slot-filling restriction precludes iterative debug-fix loops and structural refactoring, and the RQ2 "early cutoff" and "outcome equivalence" claims rely on deterministic scripted stubs over $N$ uncoupled document replicas rather than stochastic LLMs where regenerated code rarely matches byte-for-byte.

## Potential Issues And Suggestions
### [Problem Framing, Terminology, Architecture Overview & Literature Positioning] (Pages: 1-5, 17-19)
#### Potential Mistakes and Improvements

1. **Omission of Foundational Multi-Agent Systems (MAS) Coordination and Verification Literature (Sections I, II, and IX)**
   - **Potential Concern:** A major potential concern in the positioning of the manuscript is that it frames multi-agent coordination almost exclusively around recent LLM-wrapper frameworks (MetaGPT [2], ChatDev [3], AutoGen [4]) combined with build systems [20]–[22], model-driven engineering (ATL [19]), and database optimistic concurrency control (OCC [23]), while omitting over three decades of foundational research in Multi-Agent Systems (MAS). Several core architectural mechanisms presented as fresh design contributions in Sections I–III (and instantiated in Sections VI–VII) have direct, extensively studied counterparts in the classic MAS canon that are neither cited nor compared in Section II or Section IX:
     - *Environment- and Artifact-Mediated Coordination:* Design Principle 1 ("*Agents propose, the controller disposes*," Section III-A, p. 4) and the strict separation between active, autonomous agents and a deterministic controller managing passive, structured workspace objects, typed references, usage gates, and atomic guard conditions (Section II-B, p. 2) directly mirror *objective coordination* models, programmable tuple spaces/tuple centres (e.g., Gelernter and Carriero's *Linda*, *CACM*, 1992; Omicini and Denti's *TuCSoN/ReSpecT*, *Sci. Comput. Program.*, 2001; Omicini, Zambonelli, Klusch, and Tolksdorf, eds., *Coordination of Internet Agents: Models, Technologies, and Applications*, Springer, 2001/2013), and especially the **Agents & Artifacts (A&A)** metamodel (e.g., Omicini, Ricci, and Viroli, *JAAMAS*, 2008; `CArtAgO`/`JaCaMo` frameworks). In A&A and programmable coordination media, untrusted or heterogeneous agents do not coordinate merely via unstructured message passing, but emit operations/proposals on shared workspace artifacts while deterministic reactions and guards inside the coordination medium validate, transform, or reject updates outside the agents.
     - *Agent Communication Languages (ACLs), Social Commitments, and Institutional Governance:* Across Sections I–VII, the paper addresses asynchronous delays, stale replies, authority revocation, and outstanding obligations $O(S)$ by introducing custom state variables (*generation contracts*, *episodes*, *active requests*, *stamps*, *intake*, and *usable* vs. *accepted* states). In classical MAS literature, coordinating untrusted, asynchronous black-box agents without relying on their internal mental or probabilistic states is the foundational motivation for **social commitments** and commitment-based protocols (e.g., Singh, "Agent communication languages: Rethinking the principles," *IEEE Computer*, 1998; Yolum and Singh, *AAMAS*, 2002; Chopra and Singh, *JAAMAS*, 2016) as well as **Electronic Institutions** (e.g., Esteva et al., 2001; Arcos et al., *Eng. Appl. Artif. Intell.*, 2005), where deterministic runtime mediators ("governors") enforce role permissions, protocol preconditions, and active normative obligations before agent actions take effect.
     - *Formal Verification and Model Checking of Multi-Agent Systems:* Section II-F (p. 3), Section VI-C (p. 12), Section VII-C (p. 13), and Section IX ("*Specification and verification*," p. 17) ground the formal verification approach exclusively in general-purpose distributed-systems tools ($\text{TLA}^+$, TLC, TLAPS, IronFleet [24]–[27], [39], [40]). They do not situate the verification approach relative to dedicated multi-agent specification and model-checking frameworks designed explicitly to verify agent interaction protocols, epistemic/temporal properties, and compliance (e.g., Lomuscio, Qu, and Raimondi, "MCMAS: an open-source model checker for the verification of multi-agent systems," *STTT*, 2017; Wooldridge, Fisher, Huget, and Parsons, "Model checking multi-agent systems with MABLE," *AAMAS*, 2002; Dastani, Hindriks, and Meyer, eds., *Specification and Verification of Multi-Agent Systems*, Springer, 2010).
     - *Contemporary Stateful Graph Orchestrators:* While Section VII-G (*Implications for Builders of Agent Frameworks*, p. 16) briefly mentions "graph-based or conversation-based frameworks," neither Section VII nor Section IX ("*LLM-based multi-agent software engineering*," p. 17) contrasts the reference controller against contemporary stateful graph orchestrators for LLM agents (such as **LangGraph**), which natively enforce typed shared state schemas, deterministic state reducers, transactional checkpointing, and synchronization barriers.
   - **Suggested Improvement:** Even though generative LLM proposers introduce non-deterministic value synthesis and content-based invalidation nuances that differ from classical symbolic/BDI agents, constructing a coordination framework from scratch without engaging the MAS literature makes established coordination patterns appear newly invented. Expand Sections II and IX (and ground the design rules in Sections VI and VII-G) to explicitly situate the architecture within the classical MAS coordination and verification lineage as well as contemporary stateful graph orchestrators. Clearly articulate what is inherited from artifact-centric coordination (A&A, tuple centres), commitment protocols, and institutional governors versus what is uniquely required when combining non-deterministic generative proposals with fine-grained MDE trace derivation and early-cutoff build semantics, and justify the choice of $\text{TLA}^+$/TLC relative to dedicated MAS model checkers.

2. **Proliferation of Bespoke Terminology and Delayed Concrete Grounding (Sections I, II, III, and IV; Table I)**
   - **Potential Concern:** A significant potential concern regarding readability and pedagogical clarity is that Sections I–IV introduce a dense layer of custom or subtly repurposed terminology from scratch before grounding the concepts in concrete examples. Across Sections I–IV and Table I (p. 5), the reader must simultaneously track numerous overlapping abstractions:
     - *Overlapping Vocabulary for Standard Concepts:* To describe read sets and version keys for a single generated attribute, the text distinguishes between *source footprint* ($F_j$), *selected shared context*, *generation contract / contract identity* ($\eta_j$), *observation / effective observation* ($o_j$), *dependency signature* ($\sigma_j = \text{enc}(o_j)$), and *stamp* ($a$, the signature recorded at validation time), alongside *constructive structural kernel*, *structural normalizer $N_C$*, *episode nonce $e$*, *per-episode budget* ($n \le k$), *usability gate $U_j$*, *honest completion*, *publication barrier*, *observational extension*, and *lifting agent*. Many of these layer new names over standard concepts from MAS, databases, and build systems—where a footprint is a *read-set query* (or *input scope*), an observation is the *materialized read set* plus task configuration, a signature is a *content hash / Merkle rebuild key*, a stamp is the *validated read-set hash / version* in OCC, and an *episode* ($e$) is an *invalidation epoch*. Similarly, tracking subtle distinctions between *shape of the system* vs. *content* (Section II-B, p. 2), *skeleton* vs. *slot* vs. *job* vs. *binding* (Section II-C, p. 3), *intake view* (Section II-B, p. 2), and a multi-tier readiness hierarchy (*accepted*, *usable* $U_j$, and *publishable* $\mathit{Pub}$, alongside four job states *Dirty*, *Pending*, *Fresh*, *Failed* and *suspended* stages) imposes heavy cognitive load.
     - *Absence of Concrete Examples Before Abstraction in Sections II–IV:* Sections II-A through II-F introduce formal definitions (Definitions 1–3: *Request, proposal, validator*, *Metamodel, view*, *Rule, match, trace*) and core abstractions in prose before the running example is introduced in Section II-G (p. 3, right column). Notably, Section II-B (p. 2, right column) prematurely references elements of the running example—"*A clause in the intake view constrains both a patch in the implementation view and a check in the verification view*" and "*request 17*"—before the reader has been introduced to the document-service system or told what an "intake view" is. Even when Fig. 1 appears on p. 4, Sections II, III, and IV never display a concrete instance of a metamodel graph, a transformation rule $T_1$ or $T_2$, a match key $q$, a target identity $\iota(q)$, an observation tuple $o_j$, or a state tuple $S$ when they are defined.
     - *Inconsistency in "Generation Contract" Scoping:* In Section II-A (p. 2, left column), immediately following Definition 1, a *generation contract* is defined as a property of a *request* ("*We call the instruction, output schema, validator and generation settings under which a request is made its generation contract*"), and omits the validator's execution environment. In contrast, Table I (p. 5) defines *Contract* ($\eta_j$) as a property indexed by the *job* $j$ and adds "environment" ("*Identity of instruction, schema, validator, environment and generation settings*"). Furthermore, because $o_j$ already includes $\eta_j$ according to Table I, yet Step 5 of Section III-B (p. 4) states that "*The agent receives only the observation and the static instruction*," it is initially unclear whether the instruction is inside $o_j$ (via $\eta_j$) or passed alongside it, and how a job's contract relates to an individual request's snapshot.
   - **Suggested Improvement:**
     1. Move the Running Example (currently Section II-G, p. 3, and Fig. 1, p. 4) to the very beginning of Section II, and accompany Definitions 1–3, Sections II-D–II-E, and the symbolic definitions in Section IV with concrete, explicit snippets from that example (e.g., showing the exact tuple/JSON structure of the match $q$, target $\iota(q)$, job $j=(q,b)$, footprint $F_j$, observation $o_j$, stamp $a$, validator $V_j$, and state $S$ for the HTTP 409 `put(id, body)` patch).
     2. Streamline the vocabulary in Sections I–IV and Table I by aligning terms directly with standard MAS coordination, OCC, and content-addressed build-system terminology (or explicitly mapping each custom term to its standard MAS/database/build-system equivalent in Table I).
     3. Harmonize the definition and scoping of *generation contract* across Section II-A, Section III-B, and Table I so that its components (including the validator environment) and its relationship to job $j$ ($\eta_j$) versus request $u$ are unambiguous from the outset.

3. **Practicality of the Architectural Division of Labor and the Specification/Validator Bottleneck in Software Engineering (Sections I, II-B, II-C, III-A, VI, VII-G, and X)**
   - **Potential Concern:** From a software engineering standpoint, a critical potential concern regarding practical significance lies in the strict architectural restriction that "*Agents write only primitive attributes; the controller owns all objects and references*" (Section II-B, p. 2) and "*Rules thus fix the skeleton deterministically, and jobs are the slots that agents fill*" (Section II-C, p. 3; Design Principle 1, Section III-A, p. 4), raises a foundational question for the broader software engineering community: *who authors and maintains all of these formal and structural specifications in practice?* Even to coordinate the minimal four-to-five-view JSON schema in Table VI (p. 12), human engineers must pre-specify and maintain:
     1. Explicit metamodels for every software view (Definition 2) and deterministic, pure, terminating ATL-style transformation rules ($N_C$: $T_1, T_2, \dots$) with injective target constructors and disjoint producer namespaces that pre-compute the entire structural skeleton ("shape") of the system, including all target objects, multiplicities, and cross-references (Definition 3), partitioned into a strict ranked DAG (Assumptions A0 and A5);
     2. Exact, pure, total source-footprint functions $F_j(Z)$ and context-selection policies $\text{select}_{C,j}(Z)$ that anticipate all positive and negative membership dependencies across views and satisfy semantic *footprint adequacy* (Section II-D, Section X);
     3. Total, deterministic, and *sound* local validators ($V_j$) and global consistency predicates ($G$) (Definition 1, Section I "*Scope*," and Section X); and
     4. Formal $\text{TLA}^+$ specifications (`Core.tla`, `AsyncController.tla`, `AtomicController.tla`) and `TLAPS` proof modules when protocol-level verification is needed.
     
     This division of labor raises two interrelated practical challenges for the software engineering community:
     - *Structural Rigidity vs. Real-World SE Workflows:* In realistic software development tasks—such as repository-level issue resolution in SWE-agent [5] / SWE-bench [9] or multi-agent design in MetaGPT [2] and ChatDev [3], which motivate the paper in Section I—the core engineering challenge is rarely filling in isolated string or JSON slots inside a static, pre-allocated object graph. Instead, implementing a patch or test frequently reveals necessary changes to helper functions, classes, data structures, module boundaries, endpoints, or cross-file references. Requiring human engineers to pre-program deterministic transformation rules for all object creation and reference resolution reduces the agents' role to localized template slot-filling.
     - *The Specification and Validator Bottleneck:* As acknowledged in Section I ("*Scope*," p. 2) and Section X ("*Footprint adequacy and validator strength*," p. 17), coordination safety guarantees functional correctness *only* relative to what the declared validators check, and proving validator soundness in the paper's instantiation required restricting the implementation artifact language to a 6-row finite decision table where the exact reference behavior is already manually coded inside the validator (Section VI-B). For real software engineering artifacts (multi-file source code, REST APIs, prose designs, and unit test suites), sound and complete deterministic validators do not exist (parsers and finite test suites establish only weaker relations), and asking software engineers to manually author and maintain exact metamodels, dependency footprint queries, sound behavioral validators, and $\text{TLA}^+$ specifications shifts the hardest parts of software engineering back onto manual formal specification—potentially exceeding the effort of writing the software directly. Conversely, if validators are weak syntax checks or partial test suites, the framework guarantees metadata bookkeeping (no stale commits) while still permitting functionally broken software to be published.
   - **Suggested Improvement:** Address this practical engineering trade-off and return on investment directly and transparently in Sections I, III, VI, VII-G, and X:
     1. In Section I ("*Scope*"), Section III-A ("*Design Principles*"), and Section VI, clarify who is expected to author and maintain the $\text{TLA}^+$ specifications, metamodels, transformation rules, and footprints in practice—specifically distinguishing between the one-time formal verification of the generic coordination kernel in $\text{TLA}^+$ and reusable domain-independent infrastructure in `src/vgc` (performed by framework builders) versus the per-project specification burden placed on end-user software engineers, and explain how footprint extraction and structural normalization could be automated (e.g., via static AST/import call graphs) for real codebases.
     2. Explicitly distinguish in the Abstract, Section I, Section VII-G, and Section X between *coordination hygiene guarantees* (preventing stale overwrites, revoked-owner commits, and unbounded retry loops, which survive even when validators are partial/imperfect syntactic or test-suite checks) and *behavioral correctness guarantees* (which degrade when moving from a 6-row lookup table to unrestricted source code without heavy formal specification).
     3. In Section X ("*Limitations and Future Work*"), expand the discussion to address the *structural rigidity limitation* directly: explain how the framework could be extended when agents genuinely need to propose structural or architectural changes (creating new classes, endpoints, or cross-file dependencies beyond the brief mention of "Structured ingress"), and accurately scope the target domain in the Introduction (e.g., highlighting regulated MDE workflows, compliance pipelines, or schema-driven configuration synthesis rather than open-ended repository refactoring).

### [Formal Coordination Semantics & Theoretical Guarantees] (Pages: 5-11)
#### Potential Mistakes and Improvements

1. **Logical Gap in Theorem 8 (Terminal Outcome), Algorithm 1, and Reactivation Liveness Due to Deferred Structural Checks Across Suspended Stages (Sections IV-A, IV-D, V-E, VII-C, and X)**
   - **Definitive Flaw in Statement Scope, Proof, and Liveness:** In Section V-E (page 10), Theorem 8 claims that under Assumptions A0–A6 and Algorithm 1, once external input and configuration stabilize, *"the controller eventually reports either a publishable snapshot or an explicit failure, blockage or global conflict,"* and further states that *"Publication follows if every required observation is available, every dirty job obtains a committed proposal within its budget, and the resulting snapshot satisfies $G$."* However, there is an unhandled interaction between stage suspension (Section IV-A, page 6), candidate normalization during `Resolve (commit)` (Section IV-D, page 7; Table II, page 8), usable value retention in Algorithm 1 (page 10), and context restoration (`update_context` in Section VII-C, page 14).
   - **Technical Mechanism:** Section IV-A specifies that when a prerequisite stage or required context is unavailable, its dependent stage is *suspended* ($Q \neq \emptyset$) and *"contributes no active targets, traces or jobs."* Section IV-D specifies that during `Resolve`, a proposed value is installed in a private candidate state and committed *"only if every enabled structural check succeeds; otherwise the attempt counts as failed."* Because structural checks run only for *enabled* (unsuspended) downstream stages, an upstream job $j_1$ in stage $s_1$ (such as the Architecture view in Section VI-A, page 11) can commit a locally valid value $v_1$ (e.g., an integer identifier type) while its downstream consumer stage $s_2$ (the Implementation view, whose structural expression requires string identifiers) is suspended due to unavailable context. In that state, $j_1$ becomes fresh and usable ($U_{j_1}(S) = \text{true}$).
   - **Impact on Algorithm 1, Theorem 8, and Reactivation Deadlock:** When the external input or context later stabilizes so that $s_2$ should be reactivated:
     1. In the transition system (`Edit / Normalize` in Table II, page 8, and `update_context` in Section VII-C, page 14), normalizing the reactivated stage $s_2$ against the already-committed upstream value $v_1$ fails the structural normalizer $N_C$. Table II specifies that when `Edit / Normalize` fails $N_C$, the effect is *"On failure keep state, record rejection."* After catching the unhandled exception discovered in 7 of 300 reference runs in Section VII-C, the controller rejects the context-restoring transition outright. As briefly noted in Section X ("Deferred structural checks", page 17), this creates a severe **liveness hazard / deadlock**: once an upstream agent commits a locally valid value while its downstream consumer is suspended, *every subsequent attempt by the environment or an administrator to restore the context via `update_context` is rejected by the controller*, leaving $s_2$ permanently suspended ($Q \neq \emptyset$) while the upstream job $j_1$ remains `Fresh` and usable so it is never re-dispatched for repair until a human manually alters the upstream source or contract.
     2. Even if Algorithm 1 is executed stage-by-stage on the stabilized revision: at upstream stage $s_1$, job $j_1$ already satisfies $U_{j_1}(S) = \text{true}$ because its own observation $o_{j_1}$ did not change, so Line 5 (`for each job j in s with ¬U_j do`) skips $j_1$ without regenerating it. When Algorithm 1 advances to stage $s_2$, Line 4 (`normalize s; create/delete jobs; reconcile signatures`) treats stage normalization as an unconditional, non-failing imperative step, yet $N_C$ fails on $s_2$ because $v_1$ violates $s_2$'s structural constraints.
     3. The inductive step in the proof of Theorem 8 (page 10)—*"Inductively, the predecessors of each later stage are stable. If one has failed, the stage is blocked; otherwise pure normalization and observations yield a fixed finite job set with fixed signatures"*—fails when a stable, usable predecessor holds a value committed during suspension that causes downstream normalization $N_C$ to fail upon reactivation. Moreover, the sufficiency claim in the final sentence of Theorem 8 is falsified because every required observation can be available and every dirty job can succeed within its budget while the already-usable upstream job $j_1$ blocks normalization of $s_2$.
   - **Suggested Improvement:** Either (a) strengthen Assumption A1 / Definition 4 and the `Resolve` guard (Section IV-D, Eq. 5) so that candidate normalization type-checks all *configured* downstream structural expressions rather than only currently *enabled* ones, (b) add an explicit failure/invalidation branch to `Edit / Normalize` (Table II), `update_context` (Section VII-C), and Algorithm 1 (Line 4) that allows context restoration to succeed while retroactively invalidating the offending upstream job record $B_{j_1}$ (or classifies $s_2$ as structurally failed/blocked) when reactivation normalization fails, updating the request bound $k|\mathcal{J}_*|$ accordingly, or (c) add an explicit precondition to Theorem 8 excluding upstream commits made while dependent stages were suspended.

2. **Restrictiveness of Domain Assumptions (A0, A4, A5, A7) Relative to Multi-Agent Software Engineering Workflows**
   - **Potential Concern Regarding Theoretical Scope and Practical Validity:** The formal guarantees in Sections IV and V rely heavily on Assumptions A0–A7 (Table III, page 8), several of which define away core challenges of collaborative multi-agent software engineering:
     - *Strict Acyclicity and Single Producers (Assumptions A0 and A5):* Assumption A0 requires *"Finite ranked read dependencies"* where rule matches, structural expressions, observations, selectors, and validators *"read only external data or strictly earlier stages"* (page 6), and Assumption A5 requires a *"Finite acyclic dependency graph, single producers, stage stability"* where *"no output influences its own or an earlier stage's existence, validation or selection policy"* (page 10). In realistic multi-agent software engineering workflows (including the frameworks cited to motivate the work), agent coordination fundamentally relies on *cyclic, iterative feedback loops*: a downstream verification or testing agent discovers an integration bug, failing test, or security flaw that must feed diagnostic information back into the coding agent's observation to revise a patch or the design agent's observation to renegotiate an interface signature. Under A0, A5, and Algorithm 1, verification and security views sit strictly downstream of design and implementation, so their outputs cannot trigger upstream revisions; if a verification check exposes an upstream flaw or a global conflict at barrier $G$, Algorithm 1 simply halts with a terminal failure/conflict verdict (Line 14), reducing multi-agent coordination to a single-pass, feed-forward batch build pipeline.
     - *Idealization of Adequate Footprints and Sound, Total Validators (Assumptions A4 and A7, Definition 5):* Definition 5 (page 7), Assumption A7 (page 8), and Corollary 3 (page 8) guarantee domain correctness $R_j(Z, v)$ only if the footprint is semantically *adequate* ($R_j(Z, v) = \widehat{R}_j(o_j, v)$) and the local/global validators $V_j, G$ are *sound* ($V_j(o, v) \implies \widehat{R}_j(o, v)$), total, and deterministic (A4). For realistic software engineering artifacts—natural-language requirements, architectural designs, general-purpose code patches, and unit test suites—total, deterministic, and semantically sound decidable validators do not exist (as Example 1 on page 8 acknowledges). Furthermore, as shown by Counterexample 1 in Table IV (page 11), if an engineer slightly under-specifies $F_j(Z)$, the controller's exact-signature check ($\sigma_u = \sigma_j(S)$) and early cutoff (Section V-C) will mechanically certify stale downstream artifacts as "usable" and suppress necessary regeneration.
   - **Suggested Improvement:** Explicitly scope the formalism in Sections IV and V as a feed-forward, artifact-centric incremental build discipline that guarantees mechanical provenance consistency rather than general semantic correctness. Additionally, clarify how *bounded iterative feedback epochs* across stages (e.g., unrolling a cyclic test-debug-fix loop via a monotonically increasing epoch index $t \le K_{\text{epoch}}$ where downstream diagnostics from epoch $t$ are promoted into authoritative context $X^{(t+1)}$ for upstream stages in epoch $t+1$) can be represented without violating termination, and discuss what formal guarantees remain when validators are incomplete or approximate (such as finite test suites).

3. **Near-Tautological Construction of Core Theoretical Guarantees (Theorems 2, 5, 7, 9, Corollary 3, and Propositions 6 & 10)**
   - **Potential Concern Regarding Mathematical Depth:** Sections IV and V introduce a heavyweight formal apparatus—an 11-component state tuple $S = (C, X, Y, L, B, P, A, H, Q, \nu, \rho)$ and ten formal claims—where most proofs are immediate, one-step unfoldings of transition pre-condition guards and basic definitions rather than non-trivial emergent properties of a concurrent or distributed protocol:
     - *Theorem 2 (Controller safety, page 8) and Theorem 9 (Transactional reconfiguration, page 10):* Because every state-mutating transition in Table II (`Edit`, `Resolve`, `Publish`, `Reconfigure`) is defined by Assumption A3 as a coarse-grained, serialized atomic controller transaction whose pre-condition guard explicitly checks structural admissibility ($N_C$), owner authorization, signature equality ($\sigma_u = \sigma_j(S)$), local validator satisfaction ($V_j(o_u, v)$), and the publication predicate ($\text{Publishable}(S)$ in Eq. 6) on a private candidate state immediately before committing, proving by induction that reachable states satisfy these properties reduces to observing that transitions guarded by predicates (i)–(v) preserve predicates (i)–(v). For instance, Theorem 2(v) states that every installed published snapshot satisfied Eq. (6) at installation, which is literally the guard of the `Publish` transition in Table II.
     - *Theorem 5 (Exact direct invalidation, page 9):* Under Assumption A2, the signature $\sigma_j = \text{enc}(o_j)$ is defined as an injective encoding on the observation $o_j(Z)$, and the direct impact set is defined in Eq. (7) as $D(Z, Z') = \{j : o_j(Z) \neq o_j(Z')\}$. Theorem 5 proves in two sentences that a surviving job's unchanged stamp $a_j = \text{enc}(o_j(Z))$ becomes stale ($a_j \neq \sigma_j(Z')$) if and only if $j \in D(Z, Z')$. This is the literal definition of an injective function ($f(x) \neq f(y) \iff x \neq y$).
     - *Theorem 7 (Generation bound, page 9):* Within each episode, the integer counter $n$ starts at $0$, is incremented by $1$ on each `Dispatch` transition, is never decremented, and is guarded by $n < k$. Concluding that at most $k$ dispatches occur per episode ($N_{\text{dispatch}} \le k \sum_j E_j$) is an elementary property of a bounded loop counter. ### [Empirical Evaluation, Guard Ablations, Cost Analysis & Threats to Validity] (Pages: 12-18)

1. **External Validity of Omitting Real LLMs and Breakdown of "Early Cutoff" and "Outcome Equivalence" Under Stochastic Generation (Sections VII-B, VII-D, and VIII)**
   - **Potential Concern:** In Section VII-B ("Why no real LLM?", p. 13), the empirical evaluation uses zero real LLM calls, substituting deterministic or scripted adversarial Python stubs (`src/vgc`, p. 12) over a synthetic 4-view JSON document model. The author justifies this by arguing that for safety, a nondeterministic script over-approximates any LLM, and for structural cost (RQ2), *"Because the provider is deterministic in the observation, every strategy must accept identical values; we check this after every change"* (reiterated in Section VIII, p. 16: *"for structural cost, because request counts do not depend on answer quality"*). While using adversarial stubs is valid for testing state-machine safety guards in isolation (RQ1), relying exclusively on a deterministic stub that is a pure mathematical function of the observation $o_j$ introduces major validity problems for the cost, locality, and equivalence claims in **RQ2** (Section VII-D, pp. 14–15; Table VIII; Fig. 7):
     - *Unrealistic Early Cutoff Savings:* In Table VIII (p. 15) and Fig. 7, the `"Exact (ours)"` strategy achieves a $2.3\times$ overall request reduction ($10.8$ vs. $25.0$ requests per change at $N = 32$) and a $2.6\times$ reduction on contract changes ($32.0$ vs. $82.9$ requests) relative to the `"No early cutoff"` baseline.      - *Breakdown of "Outcome Equivalence":* Section VII-D (p. 14) emphasizes *"outcome equivalence: all runs"* across all five invalidation strategies as proof that *"Coarser footprints are thus sound but wasteful, and the savings never come at the price of a different result."* However, this equivalence holds in the experiment *only* because the scripted provider is a deterministic mathematical function of the target document's slice of the observation. Furthermore, to substantiate practical applicability to software engineering, supplement the evaluation with an experiment using actual LLM agents generating real code and test artifacts (e.g., on a multi-stage software engineering benchmark) to measure: (a) how often byte-exact vs. AST/semantic early cutoff actually occurs under real LLM sampling, (b) how often real LLMs trigger local vs. global validator rejections ($G$), and (c) actual wall-clock latency and token cost trade-offs.
